# Стратегия тестирования
## 1. Цели тестирования
- Убедиться, что запрос проходит по всей цепочке сервисов (gateway -> switch -> authorization service -> card management -> логи/метрики)
- Убедиться, что система принимает правильные решения по транзакциям в зависимости от статуса карты, лимита и баланса
- Убедится, что система корректно сохраняет данные о картах, лимитах и балансах
- Убедится, что неподходящие транзакции отменены с корректным кодом ответа и причиной отказа
## 2. Объект тестирования
- СМП - 11 микросервисов + PostgreSQL + RabbitMQ с гибридным взаимодействием: синхронным HTTP (авторизация, резервирование) + асинхронным RabbitMQ (логирование, уведомления);
  - Gateway Service - Единая точка входа REST API
  - Card Management - Управление картами, генерация тестовых данных
  - Switch / Router - Маршрутизация транзакций по BIN
  - Authorization - Решение APPROVED/DECLINED, проверка лимитов
  - Terminal Simulator - Эмулятор POS-терминалов
  - Merchant Simulator - Эмулятор мерчантов + эквайрера
  - Transaction Logger - Логирование транзакций + WebSocket
  - Bin Lookup	Внешний API обогащения по BIN
  - Notification Service - Уведомления о карточных событиях
  - Web Dashboard - React SPA, визуализация
  - PostgreSQL	БД - (одна, но подключаются только 4 сервиса)
  - RabbitMQ (AMQP) - Асинхронный брокер
  - RabbitMQ (Management UI) - Веб-консоль очередей
## 3. Уровни тестирования
- Unit-тестирование
- API-тестирование
- интеграционное тестирование
- end-to-end тестирование
## 4. Область тестирования
- Войдет
  - Core-сервисы Authorization и Card Management проверяются подробно(классы эквивалентности, границы, pairwise)
  - На остальные сервисы - чеклисты
- Не войдет
  - Нагрузочное тестирование - требует специальных знаний и дополнительных вычислительных ресурсов
  - Тестирование безопасности - требует отдельной экспертизы
  - Тестирование UX/UI - требует отдельной экспертизы
## 5. Подход к приоритизации 
Используем риск-ориентированные подход
- Приоритизируем негативные сценарии, наиболее влияющие на финансовую составляющую (превышения лимита, повторное резервирование средств)
- Отдаем приоритет тестированию ядровых сервисов, а не периферийных
